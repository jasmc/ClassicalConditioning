# Study artifacts, ownership and revision

Use the project's storage policy and existing publication tools. The artifact
store may be an external drive, project workspace or managed document store.
Keep reusable workflow instructions in the skill; project-specific paths and
storage obligations belong in that project's instructions. A reading catalogue
is navigation, not scientific selection state.

## A topic workspace

For a substantial guide that will evolve through discussion, prefer one editable
Markdown manuscript and its HTML reading version together. Retain an existing
structured generator/source format when replacing it would add duplication.
Keep provenance, required assets/source snapshots and exported user notes with
the topic. Add separate conversation snapshots or comparison documents only
when they preserve distinct evidence or materially aid the reader.

Use descriptive topic/scope names. Existing dated bundles can remain in place
with catalogue links; uniform names do not justify moving path-bound artifacts.
Keep retained revisions identifiable. Filename age, a folder named `current`,
and a reading-library entry do not establish scientific approval.

The editable manuscript can contain open questions, my understanding, candidate
approaches, objections and provisional preferences. Explain what is discussed,
implemented, run, validated or selected using actual evidence. A published HTML
may intentionally lag an edited manuscript; record that relationship and update
its reading pointer only after verification. Avoid two independently edited
canonical manuscripts, one in Git and another in the artifact store.

Keep supported code/tests, implementation plans, durable instructions and
approved definitions in their project-designated homes. Large teaching texts,
chat checkpoints and comparisons can live entirely in the review store when
the project chooses that policy. Retain only useful discovery and exact-version
recovery metadata in the repository. Classify by content and role, not by file
extension or a folder called `methods`.

## Decisions made together

Preserve author questions, assistant recommendations, corrections and explicit
choices as distinct statements. A provisional preference or unchecked question
is not an accepted project decision. After an explicit author choice, record
the concise decision and its scope in the existing decision/selection mechanism,
with the reviewed source/version identity and remaining limits. Keep the full
discussion in the study workspace. A decision note is not a scientific freeze;
use the project's separately authorized freeze workflow when one is requested.

## Discovery and migration

Provide one maintained entry point with scope, reading purpose, status, source
and HTML links, plus version/provenance identity. Reuse an existing catalogue
instead of creating a second latest-version authority. Explain which files are
editable sources, published guides, historical discussions or proposed plans.

Before moving an existing source or HTML, find its readers, relative assets,
hash-bound references and recorded browser origin. Snapshot original bytes and
manual edits. Verify the external copy before changing references or removing
a redundant working source. Preserve immutable/frozen originals and use exact
recovery aliases for historical dependencies; a redirect is not the original
hash-bound content. Storage unavailability means unavailable evidence, not
permission to load an older guide or fabricate a mount.

Moving HTML or changing its server/port can strand browser-local notes. Preserve
guide/storage IDs and section meanings. Export notes from the original origin
and verify compatible import in a fresh test context before retiring that route.
If existing notes have not been recovered, retain the original access path and
record that migration as incomplete. Do not read or alter the user's notebook
storage merely to test a new guide.

Verify the consumed source bytes, built HTML, required assets, download links
and catalogue target. Keep previous versions through publication. Browser
interaction and print checks apply to the guide's actual controls; static
integrity checks alone do not establish rendered usability. Report unavailable
preview capabilities honestly and use only permitted verification methods.
